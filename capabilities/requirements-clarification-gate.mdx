---
title: Requirements-Clarification Gate
description: '## What it enables'
---

When a user submits a vague build request — "build me a web app" — the team no
longer silently invents a generic scope. On the **first build of a project** the
pipeline pauses and asks the user *what to build*: a checklist of candidate
features (the common defaults pre-checked) plus a free-text box. The confirmed
feature set then drives the brief, plan, and execution.

It is the inverse of the [scope gate](/capabilities/user-feedback-system): the
scope gate trims what the brief *over-added*; this gate elicits what the request
*under-specified*. Both ask through the same universal feedback panel, so it
feels like every other question Amos asks.

The gate runs as the **first step of the code-build flow**, before the brief —
scope is settled before anything is planned.

## How it behaves

- **Every first build of a project pauses once** for confirmation. Follow-up
  prompts never re-ask, in any mode.
- Three modes: **always** (the default — every first build asks), **auto**
  (asks only when the request actually reads as vague), and **never** (the
  gate is off).
- If nobody can answer — replays and non-interactive runs — the gate stands
  down and proceeds with the recommended features instead of blocking.
- Confirmed features are folded into the brief, plan, and execution as the
  authoritative scope, and the scope gate doesn't re-flag them as inflation.
- Existing flows that don't include the gate are unaffected.
